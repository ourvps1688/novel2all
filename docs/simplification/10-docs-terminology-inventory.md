## 4. `director-follow-up.md`：重写成指路页，不要删

### 4.1 删除会立刻炸两处

1. **外部入链**：`development-roadmap.md:24` 的 `#/docs/module-director-follow-up`（见 §3.3）。
2. **构建门禁**：`pnpm check:docs-manifest` 会红。`scripts/check-docs-manifest.cjs` 要求 `site/src/docsManifest.ts` 里注册的每个 `docs/public/**.md` 都必须真实存在（stale 即 fail），而该文件在 `docsManifest.ts:135,138` 有注册。**删 md 必须同步删这两行**，漏了就是 CI 红而不是"上网之后才发现问题"。

这两条都可控，都不是不能删的理由。**真正不能删的理由在下一节。**

### 4.2 它描述的不是被删掉的功能，是被删掉的一个页面

这一点我核过服务端：**能力还在，只是不再有独立页面。**

- `/tasks/auto-director-follow-ups/:taskId`（`server/src/routes/tasks.ts:120`）与 `POST /.../actions`（`:144`）**仍然在跑**；
- `docs/simplification/03-followup-removal-assessment.md:145-146` 当时的结论就是这两处以"运行记录页在用"为由**保留**；
- 客户端也仍在消费这批数据：`api/tasks.ts:96,122` 有调用，`queryKeys.ts:111,117` 仍在定义键。

也就是说：**用户今天依然能回答"这本书停在哪、为什么停、下一步干什么"，只是答案分散在任务中心和这本书的工作台里。** 一个把这三个问题集中回答一遍的页面，对新手仍然有价值 —— 它的价值不依附于原来那个路由。

### 4.3 为什么"重写成指路"反而比"删"更符合柜台目标

用户的实际困局没变：自动导演停在某个地方了，下一步点哪。这类问题在 `faq.md`、`troubleshooting.md`、`recovery-by-phase.md` 里被反复回答，答案都指向"以前那个页面"。如果删掉，这三条链路全部失去落点。

重写的写法受 AGENTS.md UI 文案规则约束，**关键是：只说"现在在哪能做什么"，一句都不能提"原来的页面没了"**。

| 不能写 | 应该写 |
|---|---|
| 应用内注意力提醒已下线 | 想知道自动导演为什么停下，看这本书的任务中心与工作台 |
| 该功能已迁移至 XX | 暂停原因、下一步动作在 XX 就能看到 |
| 原来的应用内注意力提醒页…… | （不提它存在过） |

标题也应从模块名改成**回答的问题**，例如"自动导演停下来怎么办"这类。**标题不必由我定，我只提原则：用户在搜索的是问题，不是模块名。**

## 5. 「AI 驾驶舱」换什么：我的答案是不要停在「AI 推进状态」

> ⚠️ **本节已被 §0.1 裁决 3 取代。** 我建议的第三次改名**未获采纳**；实际动作是「只改按钮文案、不改面板名」。本节保留是为了留下"为什么考虑过又否掉"的推理链，**不要按本节执行**。

### 5.1 先说裁决原则

**文档用词必须和界面用词完全一致。** 新手是拿着文档找界面的：文档说 A、界面写 B，他会认为 B 不是他要找的东西，或者 A 功能没了。**不一致比两个都不好更糟。** 所以这是一个捆绑决定：要么一起换成新词，要么一起留着不那么好的词 —— 单独改文档会造成新的不一致。

### 5.2 「AI 推进状态」的三个问题

这个词当初是我提的，现在轮到我自己复查，结论是**不够好**：

1. **"推进"是项目管理词汇，不是写作词汇。** 用户来这里是写小说的。同类词汇（"正在推进""继续推进"）在 UI 文案规则里属过程叙述。
2. **它被当按钮使了。** `NovelProjectCard.tsx:173` 渲染的就是 `<span class="text-xs">AI 推进状态</span>`，是按钮上的可见文字。**名词短语不能当按钮标签** —— 用户不知道点下去会发生什么。按钮需要动词短语。
3. **它没有回答"我为什么要看它"。** 好的命名自带理由："进度"回答"写到哪了"，"状态"回答"（我也不知道为什么要看）"。

### 5.3 推荐改用「AI 写作进度」

| 位置 | 推荐文案 | 为什么 |
|---|---|---|
| 面板 / 弹窗**标题** | **AI 写作进度** | 说清了"谁的进度、什么事的进度"；在这个产品里，规划、角色、分卷对作者来说都是"写作"的一部分 |
| 按钮 / 链接 | **查看进度** | 动词短语，点了会发生什么是明确的 |

标题与按钮分开命名看上去多了一次决定，实际能同时解决"作标题要像个名词、作按钮要像个动作"这个长期拧巴。**如果不分开，那就统一用「AI 写作进度」，按钮上写作「查看 AI 写作进度」也算可接受。**

### 5.4 顺带查出本次换词留下的两处真问题

盘点时我顺手扫了 client 侧这批落地结果，**发现两处漏网**。它们不在本次文档范围内，但属于应当顺手修的 UI 缺陷：

1. **`NovelExistingProjectTakeoverDialog.tsx:337` 仍有"排队"二字**
   `? "自动导演接管任务已提交，可在 AI 推进状态查看排队和执行进度。"`
   「排队」在技术词移除清单里，而同一段 `:334`、`:336` 两句已经换掉了 —— 是三选一分支里漏了最后一支。这正是"不能只看前的字符串存在与否"的典型。

2. **`NovelProjectCard.tsx:169/170/173` 同一句话写了三遍**
   `title="AI 推进状态"` + `aria-label="AI 推进状态"` + 可见 `<span>AI 推进状态</span>`。
   `title` 与 `aria-label` 内容相同时读屏器会重复朗读，且 `title` 在可见文字已存在时是多余的。

### 5.5 如果决定不再做第三轮换词
