# novel2all v0.40 — Cache 架构演进收官报告

> **版本范围**：V0.29.0 → V0.40（**4 个核心 commit**）
> **完成时间**：2026-09-13
> **状态**：✅ 全部 ALL_GREEN，远端 main = `819d967`
> **核心主题**：**从"进程内 OrderedDict"到"跨 OS SQLite"**——真 LRU（V0.29）→ TTL + 持久化抽象（V0.33）→ 跨进程文件锁（V0.37）→ OS-agnostic SQLite（V0.40）

## 1. 目标

V0.24 留下 **4 个核心 Cache 需求**（按时间顺序）：

| # | 需求 | V0.29.0 | V0.33 | V0.37 | V0.40 |
|---|------|---------|-------|-------|-------|
| 1 | **真 LRU**（V0.24 是粗暴清空，命中率永远 0） | ✅ | ✅ | ✅ | ✅ |
| 2 | **TTL**（LLM 升级后旧回答失效） | ❌ | ✅ | ✅ | ✅ |
| 3 | **持久化**（重启后命中率累计） | ❌ | ✅ (JSON) | ✅ | ✅ (SQLite) |
| 4 | **跨进程/跨 OS 安全**（多进程 + 跨平台共享） | N/A | ❌ | ⚠️ (单 OS) | ✅ |

**V0.29-V0.40 主旋律**：用 4 个版本逐步把 cache 从「粗糙内存」升级为「企业级持久化」。

**关键设计原则**：
- **后端抽象**（V0.33）：`CacheBackend` Protocol 让 memory / json / sqlite 互通
- **降级策略**（V0.37）：无锁可用时 warning + 无锁运行（单进程仍安全）
- **OS-agnostic**（V0.40）：用 SQLite 替代手写锁机制，跨平台一致

## 2. 关键决策（基于真实使用数据 + 失败教训）

| # | 版本 | 决策 | 数据来源 |
|---|------|------|---------|
| 1 | V0.29.0 | **真 LRU** 用 `OrderedDict` + `move_to_end` + `popitem(last=False)` | V0.24 测试：超 max_size 时清空整个 cache 导致命中率永远 0 |
| 2 | V0.33 | **`CacheBackend` Protocol 抽象**（get/set/size/clear/stats/keys/values）| V0.24-V0.29 反复改 LRU 实现，抽象可让新 backend 零侵入 |
| 3 | V0.33 | **JSONFileBackend 优先**（不用 SQLite） | 1.28MB 数据可全加载；零新依赖；易调试 |
| 4 | V0.33 | **TTL 启动时清理 + 运行时过期** | LLM 升级后旧回答是 stale 风险（按 expires_at 删） |
| 5 | V0.37 | **跨平台锁**：`fcntl.flock` (POSIX) + `msvcrt.locking` (Windows) | POSIX 锁 / Windows 锁**不跨 OS 互斥**（接受限制） |
| 6 | V0.37 | **降级模式**：无 fcntl/msvcrt → warning + 无锁运行 | 沙箱 / 嵌入式环境可能无锁 |
| 7 | V0.37 | **锁文件 = cache 文件 + `.lock`**（atomic temp + rename） | POSIX flock 不需要内容；Windows msvcrt 需要 1 字节 |
| 8 | V0.40 | **新增 SQLiteBackend**（解决 V0.37 跨 OS 限制） | SQLite 内置锁机制跨 POSIX/Windows 通用 |
| 9 | V0.40 | **WAL 模式**（reader 不阻塞 writer） | SQLite 默认 rollback journal 模式下 reader 阻塞 writer |
| 10 | V0.40 | **`threading.Lock` 包裹 DB 操作**（同连接多线程不安全） | sqlite3 `check_same_thread=False` 仅禁运行时检查，不解决并发问题 |
| 11 | V0.40 | **`encode_key` 统一接口**（不需 JSON serialization） | tuple key 通过 `:` 拼接，所有 backend 共用 |

## 3. 完整 commit 链路（4 个核心 commit）

### 3.1 V0.29.0 真 LRU — `ea52a89`

**问题**：V0.24 应用层 cache 是 `dict` + 粗暴清空：
```python
if len(self._cache) >= self.config.cache_max_size:
    self._cache.clear()  # ← 一刀切，命中率归零
```

**修复**（`core/provider.py`）：
- `self._cache: OrderedDict`（V0.29+）
- `get` 时 `move_to_end` 更新"最近使用"

**测试**：`tests/unit/test_provider_router.py::TestCacheLRUV029`（3 个）+ `TestPromptCacheV024` 兼容性更新

### 3.2 V0.33 Cache TTL + 持久化 — `6983a58`

**问题**：进程内 OrderedDict 重启清零 + 无 TTL（LLM 升级后旧回答失效）。

### 3.3 V0.37 跨进程文件锁 — `4dd9c40` + 2 fix

**问题**：V0.33 JSONFile 多进程并发写会损坏文件（V0.33 接受 race condition）。

**修复**（`core/cache.py` 加 `CacheLock` 类 + 188 行）：
- 新增 `CacheLock` 类（上下文管理器）：
  - POSIX → `fcntl.flock(LOCK_EX | LOCK_NB)`
  - Windows → `msvcrt.locking(LK_NBLCK, 1)`
  - 无可用模块 → warning + 无锁（单进程仍安全）
- `JSONFileBackend._save()` 用 `with CacheLock(self._path):` 包裹
- `stats()` 加 `lock_backend` 字段

**CI 反复修**（3 commit 收尾）：
1. `4dd9c40` 初版：CI 失败（4 个 POSIX job）
2. `2ea1418` fix multiprocess 测试（subprocess cwd 不一致）
3. `72b307d` fix reentrant + degrade 测试（POSIX 行为差异）

**关键 Windows 陷阱**：
```python

# ✅ 用 O_BINARY 显式二进制 + fdopen("rb+")

```

**测试**：8 unit（基础 + 后端探测 + 集成 + 持久化 + 多线程 + 多进程 + 降级 + LLMProvider）

### 3.4 V0.40 SQLite backend（OS-agnostic） — `819d967`

**问题**：V0.37 跨 OS 锁不互斥（POSIX 锁 vs Windows 锁）。需要 OS-agnostic 方案。

**修复**（`core/cache.py` 加 `SQLiteBackend` 类 + 188 行）：
- 新增 `SQLiteBackend`（零新依赖，sqlite3 是 Python 标准库）
- WAL 模式 + `INSERT OR REPLACE` 原子 upsert
- `threading.Lock` 包裹所有 DB 操作（sqlite3 同连接多线程不安全）
- `LLMConfig.cache_backend` 扩展 `Literal["memory", "json", "sqlite"]`
- 默认路径：`.novel2all/cache.db`

**SQLite Schema**：
```sql
CREATE TABLE cache (
    key TEXT PRIMARY KEY,
    value TEXT NOT NULL,
    expires_at REAL,
    last_accessed_at REAL NOT NULL,
    created_at REAL NOT NULL
);
CREATE INDEX idx_last_accessed ON cache(last_accessed_at);
```

**关键 TTL bug 修复**（V0.40 过程中发现）：
```python
# ❌ 错：cutoff 算两次 ttl
cutoff = time.time() - self._ttl_seconds
DELETE WHERE expires_at < cutoff
# 等价于 DELETE WHERE (now_set + ttl) < (now - ttl)
# 实际删除的是 now_set < now - 2*ttl 的条目（错！）

# ✅ 对：cutoff 就是 now
cutoff = time.time()
DELETE WHERE expires_at < cutoff
# 正确删除：expires_at < now（已过期）
```

**测试**：21 unit（set/get/overwrite + tuple key + TTL + LRU + 持久化 + 4 线程并发 + WAL + schema + LLMConfig 集成 + close + lock_backend="sqlite"）+ 4 e2e

## 6. 关键技术细节

### 6.1 真 LRU 语义（V0.29.0）

```python
# 写入新条目
self._cache[key] = value  # 自动放最末

# 读 cache
self._cache.move_to_end(key)  # 移到最后（最近使用）

# 超 max_size
if len(self._cache) >= self.config.cache_max_size:
    self._cache.popitem(last=False)  # 删最旧（头部）
```

**为什么 move_to_end**：OrderedDict 的 `__getitem__` 不会自动更新位置，必须显式调 `move_to_end`。

### 6.2 CacheBackend Protocol（V0.33）

```python
from typing import Any, Protocol

class CacheBackend(Protocol):
    def get(self, key: tuple | str) -> str | None: ...
    def set(self, key: tuple | str, value: str) -> None: ...
    def size(self) -> int: ...
    def clear(self) -> None: ...
    def stats(self) -> dict[str, Any]: ...
    def keys(self) -> Iterator[str]: ...  # V0.40: 用于跨进程 LRU 测试
    def values(self) -> Iterator[str]: ...  # V0.40: 同上
```

**为什么用 Protocol 而非 ABC**：PEP 544 structural subtyping — 后端只需实现方法签名，无需继承。JSONFile / MemoryLRU / SQLite 都"鸭子类型"实现。

### 6.3 JSONFile atomic write（V0.33）

```python
def _save(self) -> None:
    """原子写入：temp file + rename"""
    with tempfile.NamedTemporaryFile(
        mode="w", encoding="utf-8",
        dir=self._path.parent,
        prefix=f".{self._path.name}.",
        suffix=".tmp",
        delete=False,
    ) as tmp:
        json.dump({"version": FILE_VERSION, "entries": self._entries}, tmp, ensure_ascii=False)
        tmp_path = tmp.name
    Path(tmp_path).replace(self._path)  # atomic rename
```

**为什么 temp + rename**：POSIX `rename(2)` 是原子操作；写临时文件后 rename 避免读到部分写入。

### 6.4 CacheLock 跨平台（V0.37）

```python
class CacheLock:
    def __init__(self, target_path: Path) -> None:
        self._backend: str = "none"
        if sys.platform == "win32":
            try: import msvcrt; self._backend = "msvcrt"
            except ImportError: pass
        else:
            try: import fcntl; self._backend = "fcntl"
            except ImportError: pass

    def __enter__(self) -> Self:
        if self._backend == "none": return self
        # O_BINARY 必须（Windows msvcrt 需要）
        self._fd = os.open(
            self.lock_path,
            os.O_CREAT | os.O_RDWR | os.O_BINARY,
            0o644,
        )
        self._fd = os.fdopen(self._fd, "rb+")
        if self._backend == "fcntl":
            fcntl.flock(self._fd.fileno(), fcntl.LOCK_EX | fcntl.LOCK_NB)
        elif self._backend == "msvcrt":
            msvcrt.locking(self._fd.fileno(), msvcrt.LK_NBLCK, 1)
        return self
```

**V0.37 限制**：不同 OS 的锁不互斥（POSIX 锁 vs Windows 锁）。多 OS 共享 cache 文件不安全（V0.40 解决）。

### 6.5 SQLite WAL 模式（V0.40）

```python
# 启用 WAL 模式（reader 不阻塞 writer）
self._conn.execute("PRAGMA journal_mode=WAL")
self._conn.execute("PRAGMA synchronous=NORMAL")  # 性能/安全平衡
```

**WAL 优势**：
- reader 不阻塞 writer（只读 WAL snapshot）
- writer 不阻塞 reader
- 比默认 rollback journal 模式并发更好

**WAL 代价**：
- 产生 `.db-wal` / `.db-shm` 辅助文件
- 备份时需要同时复制 3 个文件（或先 PRAGMA wal_checkpoint(TRUNCATE)）

### 6.6 SQLite 多线程安全（V0.40）

```python
# sqlite3 同连接多线程不安全（即使 check_same_thread=False）
# 需要手动加 threading.Lock
self._lock = threading.Lock()

def get(self, key):
    with self._lock:
        row = self._conn.execute("SELECT ...").fetchone()
        # ...

def set(self, key, value):
    with self._lock:
        self._conn.execute("INSERT OR REPLACE ...", ...)
        self._evict_if_needed()
```

**为什么不每线程一个连接**：FastAPI 线程池线程数动态变化（默认 40），开 40 个连接太重；用单连接 + lock 更轻量。

### 6.7 encode_key 统一接口（V0.33）

```python
def encode_key(key: tuple | str) -> str:
    """统一 key 编码：tuple 用 ':' 拼接，str 原样。"""
    if isinstance(key, str):
        return key
    return ":".join(str(part) for part in key)
```

**为什么不是 JSON**：
- 简单（tuple 元素都是 str/float/int）
- 短（`a:1:2:3.0` vs `{"a": 1, ...}`）
- 不需要 json 依赖（虽然 json 是 stdlib）

### 6.8 V0.24 向后兼容（V0.33 shim）

```python
@property
def _cache_hits(self) -> int:
    return getattr(self._cache, "_hits", 0)

@_cache_hits.setter
def _cache_hits(self, value: int) -> None:
    if hasattr(self._cache, "_hits"):
        self._cache._hits = value
```

**为什么需要**：V0.24 测试直接 `provider._cache = OrderedDict()` + `provider._cache_hits = 0`（测试内部状态）。V0.33 重构后 `_cache` 是 backend 对象，测试要更新；为保留旧测试，加 property 兼容。

| 1 | `LLMProvider._cache_hits/_cache_misses` property shim 仅支持 V0.24 测试 pattern | 旧测试可继续用 | V0.42+ 移除 shim，要求测试用 `provider.cache_stats()["hits"]` |
| 2 | SQLiteBackend 多线程需 `threading.Lock`（单连接） | 简单但非最优 | V0.42+ 用连接池（每线程独立连接） |

| 4 | LLMProvider 启动时不显式 close SQLite 连接 | 依赖进程退出 | V0.42+ 加 `provider.close()` 显式 close |
| 5 | cache.db 损坏时不会自动恢复 | 需要手动删 db 重启 | V0.42+ 加 PRAGMA integrity_check + 自动 backup |

### 8.2 未来工作候选

- **V0.42**: 连接池（thread-local SQLite connection）+ 自动 backup
- **V0.43**: 多 backend 切换（运行时不丢数据，json → sqlite 平滑迁移）
- **V0.44**: Cache 预热（启动时从外部源加载热门 entries）
- **V0.45**: 缓存压缩（>1MB 自动 gzip）
- **V0.46**: LLM 响应结构化校验（cache 命中但 schema 变了时自动失效）

## 13. 未来 AI 助手接手 Cache 模块必读清单

> 如果你是新接手 Cache 模块的 AI 助手，请按以下顺序阅读：

### 1. 必读（3 个文件 + 本文档）

1. **`src/novel2all/core/cache.py`**（702 行）—— 三个 backend 的完整实现
2. **`docs/llm-providers-truth.md` §1-§7**（V0.23 cache 决策）
3. **本文档** —— Cache 演进 V0.29 → V0.40

### 2. 关键设计原则

| 原则 | 实施 |
|------|------|
| **后端抽象** | `CacheBackend` Protocol，新 backend 只需实现方法签名 |
| **TTL 算法** | `expires_at = now + ttl_seconds`（直接比较 `expires_at < now`）|
| **LRU 淘汰** | 按 `last_accessed_at ASC` 删除（无论 OrderedDict 还是 SQLite）|
| **SQLite 多线程** | `threading.Lock` 包裹所有 DB 操作（sqlite3 同连接不安全）|
| **JSONFile 原子写** | temp + `os.replace`（atomic rename）|
| **跨平台锁** | fcntl (POSIX) / msvcrt (Windows) / 降级 none |

### 3. 永远不要做的事

- ❌ **不要用 `dict.clear()` 替代 LRU 淘汰**（V0.24 教训，命中率归零）
- ❌ **不要把 tuple key 直接当 SQLite PRIMARY KEY**（用 `encode_key` 转为字符串）
- ❌ **不要用 `cutoff = time.time() - ttl_seconds`**（错！cutoff 应该是 `time.time()`）
- ❌ **不要让 sqlite3 同连接多线程访问**（加 `threading.Lock`）
- ❌ **不要在 msvcrt 路径用 `open("w")` 模式**（用 `os.open(O_BINARY)` + `os.fdopen("rb+")`）
- ❌ **不要跨 OS 共享 JSONFile cache**（POSIX 锁 vs Windows 锁不互斥，V0.40 SQLite 解决）
- ❌ **不要忘记更新 V0.24 测试 pattern**（用 `provider.cache_stats()["hits"]` 替代 `provider._cache_hits`）

### 4. 添加新 backend 步骤

1. 实现 `CacheBackend` Protocol 的所有方法
2. 在 `LLMConfig.cache_backend` Literal 加新值
3. 在 `LLMProvider.__init__` 加 elif 分支
4. `stats()` 返回 dict 含 `backend/lock_backend/persist_path` 字段
5. 加单测（基础 + TTL + LRU + 跨实例持久化 + 线程安全）
6. 加 e2e（如需前端展示，更新 `cache_panel.html`）
7. CI 跑全 14 jobs

### 5. 调试速查

| 错误 | 原因 | 解决 |
|------|------|------|
| `'NoneType' object is not subscriptable` | sqlite3 跨线程 | 加 `threading.Lock` |
| `database is locked` | SQLite 超时 | 增 `timeout=5.0` |
